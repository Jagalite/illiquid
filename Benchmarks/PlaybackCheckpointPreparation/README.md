# Checkpoint construction: performance research

**Disposition: retain the evidence; do not open an additional performance PR.**
The original experiment found a useful reduction in large-playlist checkpoint
construction. [PR #124](https://github.com/Jagalite/illiquid/pull/124), opened
concurrently during this investigation, independently implements the same
optimization and now includes its own native qualification. A duplicate PR
would add no distinct production benefit.

A separate lazy-source experiment against that PR consistently saved about
6 microseconds for short playlists whose items all have unsupported persistence
identities. Its ordinary-playlist controls were mixed, including unfavorable
medians for a 10,000-item folder playlist. This evidence does not establish
common-path non-regression. Moving item normalization before source validation
also creates a concrete tradeoff for unsupported source identities. The narrow
edge-case benefit does not justify proposing this additional change.

This research branch retains the measured lazy candidate, tests, reproducible
runner, and all completed and interrupted evidence. The candidate is an
experiment, not a recommendation to merge. No production PR was opened by this
study, and main was not changed.

## Results and decision

### Original improvement, now covered by PR #124

The first candidate skips membership scans when no collection folder exists
and prepares the current source identity once for eligible folder playlists.
Against original main `ea2ff568237e2667f7b1aeee67b11a44ebe95b72`, the completed
Linux experiment measured the following full `record()` costs. Values include
the unchanged record construction and playlist deduplication.

| Workload | Main CPU median, ms | Eager candidate CPU median, ms | Median paired CPU reduction |
| --- | ---: | ---: | ---: |
| Folder, last match, 1,000 items | 16.093 | 10.662 | 32.94% |
| Folder, last match, 10,000 items | 150.761 | 99.357 | 35.04% |
| No folder, last match, 1,000 items | 14.768 | 5.333 | 62.42% |
| No folder, last match, 10,000 items | 154.933 | 56.541 | 63.95% |
| No folder, missing source, 1,000 items | 14.725 | 4.863 | 67.60% |
| No folder, missing source, 10,000 items | 147.417 | 57.254 | 61.05% |

All six pairs favored the candidate in each displayed workload. These are
selected long-scan workloads, not a summary of every case: 10 of 58 cells had
unfavorable paired CPU medians, and 11 had unfavorable wall-time medians.
The complete [eager evidence](evidence/linux-eager/RECEIPT.md) retains all 696
observations, calibration, correctness checks, and the separate smoke run.
These savings overlap PR #124 and are not additional gains from the lazy
candidate below. PR #124's separately authored native results are available

The all-unsupported-items fixture has a valid local current source, a supplied
folder, and HTTPS playlist entries. It is an adverse-input case, not a typical
folder-discovery playlist. The one-item CPU reductions ranged from 95.25% to
96.39%; the 32-item reductions ranged from 22.97% to 50.74%. All six pairs
improved in each of these two cells. The 1,000-item result was less consistent.

The long-folder case favored the candidate in only one pair, with paired CPU
changes spanning both large gains and large losses. Variation in remote and
other controls suggests substantial shared-host noise, but does not establish
that the unfavorable measurements are harmless. No general speedup or tight
equivalence is claimed for the lazy candidate.

There is also an algorithmic tradeoff: when a source file URL passes `isFileURL`
but has an unsupported persistence identity, such as a nonlocal authority, the
lazy candidate normalizes an item before rejecting that source; with an
unsupported prefix it scans that prefix. HTTPS sources still short-circuit
before this work. The eager parent can reject an unsupported source identity
immediately. The current direct timing profile measures a 1,000-item
unsupported-source control but does not quantify all small or combined-invalid
cases. A briefly reviewed two-phase variant removed the repeated optional-key
branch from the remaining scan, but retained this tradeoff. It was not
benchmarked or published and was discarded; no test or performance claim here
applies to it.

## Checkpoint context

`PlaybackController` captures a checkpoint when playback position moves at
least ten seconds from the last checkpoint, and on operations including pause,
playlist changes, source commitment, and shutdown. A serial persistence writer
constructs the record before saving it. The work measured here is on that
background writer, not the main actor.

Opening several individual files and appending files create playlists without
a collection folder. Previously, record construction still scanned these
playlists to determine whether the source belonged to the collection. The
answer could not affect the saved folder because the supplied folder was nil.
For playlists with a folder, the scan normalized the same source URL for each
supported item visited.

The parent optimization skips membership scans for absent folders and empty
playlists. This follow-up waits for the first supported playlist item before
preparing the source identity. Unsupported-only playlists never normalize the
source. A missing identity never matches another missing identity. Source URL
validation, the original supplied folder,
item order and metadata, saved index, shuffle IDs, schema, position sanitization,
and timestamp construction retain their existing contracts.

`PlaybackSessionRecord` still deduplicates the playlist. Both arms include this
unchanged work. The change introduces no persistent cache, filesystem lookup,
new concurrency, or serialization format.

## Reproduce

Run from a checkout containing the baseline Git object, using Swift 6.1 or
later. The package's macOS deployment boundary remains macOS 26. Follow the
repository's `AGENTS.md`: submit builds to Kyoto when available, and serialize
builds sharing a build directory. The dedicated GitHub workflow handles that
queue check on its hosted runner.

```sh
python3 Benchmarks/PlaybackCheckpointPreparation/run.py \
  --output /tmp/checkpoint-identity-followup --pairs 6 --target-ms 250 \
  --baseline pr124 --profile incremental
```

The output directory must be new or empty. Dependencies are included in the
repository; these component packages need neither FFmpeg nor the full app.
Use `--baseline main --profile full` to run the broader main-based matrix for
the currently checked-out candidate. Reproducing the historical eager result
requires its archived candidate commit or exact source snapshots, identified
in the [eager receipt](evidence/linux-eager/RECEIPT.md); the retained lazy source
is a different implementation. The full profile also accepts
`--quick --pairs 2 --target-ms 25` for a shorter mechanics check.
`--tests-only` and `--skip-tests` select a phase.
The incremental profile always uses its exact ten predefined workload IDs.

## Source isolation and correctness

The runner pins both supported baseline commits and full-file SHA-256 hashes
for seven baseline production files.
Only `PlaybackCheckpointWriter.swift` changes between the two arms. Both use
the same current core sources, regression tests, bridge, and driver. The runner
rejects changed unrelated dependencies.

Six Foundation core inputs provide the actual playlist, URL, source, and
session-record implementation. `PlaybackSessionStore.swift` is cut at a checked
boundary after the **complete `PlaybackSessionRecord` and `PlaybackSessionStoring`
declarations**. Its unused disk-store class and macOS signposting dependencies
are outside this experiment. The full checkpoint source is compiled unchanged;
no replacement production declarations are used.

Identical tests run against baseline and candidate in debug and release. The
parent checkpoint suite is retained unchanged. The added identity suite
exercises raw and relative URLs, encoded dot segments,
localhost and rejected authorities, NFC/NFD Unicode, duplicate metadata, nil
folders, malformed source enum cases, and stale saved indices. It includes
1,190 small-playlist comparisons of every record field and sorted-key JSON
bytes with the original pipeline. Independent fixture labels check membership
as well. Each constructor samples its own clock; only `updatedAt` is aligned
for byte comparisons, and a separate test bounds it by the call's start/end.

Before timing, separate executables emit complete canonical records for all
58 workload fixtures. The runner requires byte-identical output, including when
only ten cells are timed. Every timed process independently checks the complete
fixture before and after measurement,
normalizing only the sampled timestamp. Unicode fixtures must retain distinct
raw source/item URL spellings with equal normalized identities.

## Measurement protocol

Each arm builds optimized `IlliquidCore` and `IlliquidPlayer` libraries, then
compiles the identical driver separately. A small non-inlinable bridge exposes
the internal checkpoint constructor without changing its production visibility.
No cross-module optimization is enabled. Variant-specific loader paths prefer
the recorded libraries over inherited research paths; dependency and command
receipts retain the resolution setup.

All 58 fixture cells are still checked for complete output equality. The
primary incremental timing profile selects exactly these ten cells:

- Unsupported playlist items at 1, 32, and 1,000 items.
- Folder first match at 1 and 32 items.
- Folder last match at 1,000 and 10,000 items.
- No-folder last match, remote source, and unsupported source at 1,000 items.

The broader main-based timing profile contains these 58 cells:

| Fixtures | Playlist sizes |
| --- | --- |
| Folder: first, middle, last, missing source | 0, 1, 32, 1,000, 10,000 |
| No folder: first, last, missing source | 0, 1, 32, 1,000, 10,000 |
| Remote source with a supplied folder | 0, 1, 32, 1,000, 10,000 |
| Long Unicode source alias, with and without a folder | 1, 32, 1,000 |
| Unsupported source; all unsupported playlist items | 1, 32, 1,000 |
| Duplicate items, with and without a folder | 1, 32, 1,000 |

Fixture construction, complete semantic checking, and serialization occur
outside timing. The measured loop includes full record creation, its unchanged
deduplication, a small result checksum, and record destruction. Darwin drains
an autorelease pool for each operation in both arms. Each process warms two
calls before measurement. `Date()` remains part of the production call.

Calibration runs both variants, starting with one call, and selects a common
iteration count targeting 250 ms of CPU time in the faster arm. At most three
calibration trials are used, with a one-million-iteration cap. Actual durations
are retained; the target is not a guarantee for every observation. Six fresh
process pairs per cell alternate baseline-first and candidate-first order.
Both `CLOCK_PROCESS_CPUTIME_ID` and monotonic elapsed time bracket the same work.
No timing overhead is subtracted and no measured observations are discarded.

Absolute values are medians of per-process average costs. Paired percentage
reductions are the median of `100 * (1 - candidate / baseline)` across six
pairs; they need not equal the percentage calculated from the two displayed
absolute medians. The summary retains ranges, every paired reduction, and the
number of pairs favoring the candidate for both clocks. CI has no noisy timing
pass/fail threshold.

## Interpretation limits

These are in-memory component measurements with synthetic playlists. They
exclude JSON encoding, atomic disk writes, writer-queue coalescing, media
decoding, UI layout, and playback rendering. They do not establish a whole-player
CPU, frame-rate, energy, memory, shutdown-latency, or storage-throughput gain.

First-item matches, empty playlists, and remote sources have little or no
membership work to remove. The first experiment eagerly prepared the source
key, which added unnecessary work for an all-unsupported playlist. Its retained
adverse observations motivated the final lazy preparation. Those controls remain
in the unchanged fixture matrix for both experiments.
Native app integration would be checked separately by the repository's
restoration/native lifecycle workflow. No additional PR was opened because
the completed incremental study did not justify shipping its candidate.

## Earlier experiments

The primary PR #124 comparison is separate from two earlier main-based studies:

- [Eager-source experiment](evidence/linux-eager/RECEIPT.md): a completed
  58-cell study with 696 measured observations, plus matching four-configuration
  tests and a separate short smoke cohort. It showed large-playlist savings
  that overlap PR #124, while the all-unsupported singleton control increased
  from 0.205 to 4.746 microseconds of CPU per record. This adverse result led to
  lazy source preparation. All observations remain available.
- [Interrupted revised-versus-main experiment](evidence/linux-revised-incomplete/RECEIPT.md):
  disk exhaustion interrupted the repeat after 41 complete timing cells. The
  final manifest was lost, the command ledger ends with a partial line, and
  the raw summary still says `running`. The separate external status receipt
  records process exit 1 and the disk error. Unsupported-item timing cases had
  not been reached. This is incomplete historical evidence, with no final
  provenance pass; it is not used as the follow-up's qualification result.

The initial sandboxed compiler failure is retained separately in the eager
experiment's receipt. It produced no completed tests or timing observations.
